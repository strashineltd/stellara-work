| 项 | 结论 |

### 🎯 关键技术发现：js-sdk 有官方 Node 构建

- 关键方法：`signUp` / `signInWithPassword` / `signInWithOtp` / `getUser` / `getSession` / `setSession` / `refreshSession` / `isUsernameRegistered`

### 注册/登录流程（CloudBase v2 语义）
```
注册：signUp({ email, password, username?, name? })  →  发验证码到邮箱
      ↓ 返回 data.verifyOtp（是个**函数**，不能跨 IPC）
      主进程暂存到 Map，用 pendingId(UUID) 引用（TTL 9 分钟）
      ↓
      data.verifyOtp({ token: code })  →  自动注册并登录
登录：signInWithPassword({ email|username|phone, password })
      → 含 @ 视为邮箱，否则视为用户名
```

### 设计要点

### 🎯 关键技术突破：绕过 mcporter 守护进程

`mcporter@0.13.10` 要求 **Node ≥24**（本机 22.22.2），其 keep-alive 守护进程会卡死：
- 报 `Transport ownership could not be verified` / `Daemon is draining` / `connect ENOENT user.sock`
- `daemon stop/start` 都救不回来

**解法：内联 stdio，每次调用现拉一个 MCP 进程，完全不用守护进程**
```bash
npx --yes mcporter@latest call cb.<tool> key=value \
  --stdio npx --stdio-arg --yes --stdio-arg @cloudbase/cloudbase-mcp@latest --name cb \
  --output json
```

**但内联方式无法完成设备码登录**：每次调用是新进程，设备码的轮询/令牌落盘需要常驻进程。
→ 改用 **`tcb login --flow device`**（常驻轮询 + 落盘凭证），**MCP 与 CLI 共享同一套凭证**，
  登录成功后内联 MCP 立刻就能用。

**`tcb` CLI 安装陷阱**：`@cloudbase/cli` 有 3 个 bin（`tcb`/`cloudbase`/`cloudbase-mcp`），
`npx @cloudbase/cli` 会报 `could not determine executable to run`。必须指定：
```bash
npx --yes -p @cloudbase/cli@latest tcb <command>
```
登录后会交互式问遥测（Y/n）——登录已完成，直接 `pkill` 掉即可。

### 🔑 邮箱登录的两层配置（重要，容易漏）

只调 `patchLoginStrategy { email: true }` **不够** —— 返回 `success: true` 但 `loginMethods.email` 仍是 `false`。
必须**同时**配置 provider 层：

```bash
# ① 登录方式开关
manageAppAuth action=patchLoginStrategy patch={"email":true}

# ② provider 层（缺这步 email 不会变 true）
manageAppAuth action=updateProvider providerId=email providerType=EMAIL \
  config={"On":"TRUE","EmailConfig":{"On":"TRUE","SmtpConfig":{}}}
```
（对照：短信只需 `patch={phone:true}`，因为它走云开发默认短信通道，无需配 provider）

### 探测脚本的坑

### 决定性手段：用临时邮箱自己做端到端实测

用 `api.mail.tm`（域名 `uberip.com`）建临时邮箱 → 真实调 `signUp` → 轮询收信 → `verifyOtp`：

```
[1] 创建临时邮箱: sx3e648a60@uberip.com ✅
[2] signUp → error: null，data 字段只有 verifyOtp，verifyOtp 是 function
[3] 第 12s 收到邮件，发件人 cloudbase_noreply@tencent.com，验证码 157640
[4] verifyOtp → error: null，返回 user（只有 email，uid undefined）+ session
*** 全链路成功！ ***
```

**结论：云端 / 邮件通道 / SDK / Publishable Key / 整条链路 100% 正常。** 问题在应用侧。

### 定位过程（日志排查法）

`~/Library/Logs/stellara-work/main.log`：
- `22:30:43 云注册验证码已发送: 2041366386@qq.com` —— 发码成功
- 之后**再无任何云账号日志**
- 全文只有 1 条 `[warn]`（17:32 的 safeStorage），说明**日志能记 warn**，但云账号操作没触发

### 🐛 真正的根因（我自己的代码）

旧代码：
```ts
if (res.error) return { ok: false, error: describeCloudError(res.error) };  // ← 直接返回，没走 fail()，所以不留日志！
```
所以 **SDK 确实被调用了、也确实拒绝了验证码**，只是这条分支不打日志，导致排查时误以为"没走到 SDK"。
`describeCloudError` 会把 SDK 的**原始中文错误**放进 `message`，所以用户看到的是 SDK 的措辞（含"失效"）。

**最可能的触发条件**：验证码 10 分钟有效期。发码 22:30:43 → 用户提问 22:37，若等到 QQ 邮箱送达后再慢慢输入，极易超时。
（QQ 邮箱送达延迟本身也可能吃掉几分钟）

### 🔧 本次修复（3 处）

1. **加诊断日志**：`verifySignUp` 的每个提前返回分支 + SDK 拒绝分支都 `log.warn`，
   带上 `pendingId` 和 SDK 原始错误（截断 300 字符）。以后同类问题一眼可查。
2. **`verifyOtp` 的 this 绑定**：原来 `const verifyOtp = res.data?.verifyOtp` 解构后存 Map，
   再 `pending.verifyOtp(...)` 调用，`this` 变成 Map 条目对象而非 `res.data`。
   改为 `(params) => res.data.verifyOtp(params)` 保持成员调用语义。
   （实测直接调用 `up.data.verifyOtp({token})` 是通的，所以这个隐患在别的 SDK 版本可能爆）
3. **注册会话跨组件卸载保留**：`SettingsPanel` 用 `key={tab}`，切设置页签会卸载本组件，
   `pendingId` 的 state 随之丢失 → 用户「拿码 → 切页签 → 切回」就会看到会话失效。
   改为模块级缓存 `pendingSignUpCache = { pendingId, email, expiresAt }`。
