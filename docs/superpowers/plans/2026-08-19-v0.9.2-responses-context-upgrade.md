# Stellara Work v0.9.2 Responses-native Agent 整体修改方案

**状态：** 仅规划，尚未执行

**目标版本：** v0.9.2

**目标平台：** Windows 11 x64、macOS 14/15 arm64

**Goal：** 废除 Chat Completions 传输格式，将模型调用、Agent 工具循环、上下文管理和子代理编排统一升级为 Responses API；建立本地无状态 Items 日志和 Context Hub，使计划、文件、工具、验证、记忆、子代理和 UI 形成可追踪、可恢复、可验证的上下文联动。

**Architecture：** Electron 主进程维护会话级 Context Hub 和 Responses Items；所有供应商统一调用 `POST {baseUrl}/responses`；每次请求固定使用本地上下文重放，不依赖 `previous_response_id` 或供应商服务端会话；Agent、子代理和 Renderer 通过带 revision 的上下文事件同步。

**Global Constraints：**

- 全程 TDD，先写协议契约和失败测试，再实现。
- 不保留 `/chat/completions` 回退路径。
- 不新增 Anthropic Messages 适配器。
- 不删除用户旧配置、旧会话或 API Key。
- API Key 继续只存在于主进程，Renderer 只能获得 `hasKey`。
- 所有 UI 文案使用中文；沿用现有 design tokens，不整体重做视觉风格。
- 每个任务完成后运行定向 Vitest、`npm run typecheck` 和 `git diff --check`。
- 发布前运行全量测试、Windows/macOS 构建和真实供应商冒烟测试。

## 1. 已确认的产品决策

### 1.1 协议决策

v0.9.2 只允许 Responses API：

```text
POST {baseUrl}/responses
```

废除以下网络格式和解析逻辑：

- `/chat/completions`
- `messages + choices`
- `choices[0].delta`
- `delta.tool_calls`
- `tool_call_id`
- `data: [DONE]`
- Anthropic Messages
- 用户可选择的 API 协议字段

UI 中仍然可以使用“消息”“对话”等产品概念，但这些领域对象不得直接作为供应商请求体。

### 1.2 上下文决策

统一采用本地无状态模式：

- 每次请求发送 `store: false`。
- 不使用 `previous_response_id`。
- 不使用 Conversations API。
- 不依赖供应商保存历史。
- 主进程在本地保存 typed Responses Items。
- 下一轮请求重放经过预算裁剪的历史 Items。
- `instructions` 每次请求重新生成。

原因：DeepSeek Responses API 明确不支持 `previous_response_id`、`conversation` 和服务端存储；统一采用共同能力子集可以保证 DeepSeek、Qwen 和自定义端点行为一致。

### 1.3 模型准入决策

| 模型 | Base URL | Responses 状态 | v0.9.2 处理 |
|---|---|---|---|
| DeepSeek-V4-Flash | `https://api.deepseek.com` | 官方支持 | 新增并正式启用 |
| DeepSeek-V4-Pro | `https://api.deepseek.com` | 官方支持 | 保留并迁移 |

## 2. 当前实现与目标差距

### 2.1 当前模型层

- `electron/llm/openai-compat.ts` 只支持 Chat Completions。
- `electron/llm/endpoint.ts` 会按厂商猜测 `/v1/chat/completions`。
- `electron/config/model-configure.ts` 和 `electron/main.ts` 直接实例化 `OpenAICompatClient`。
- `electron/agent/loop.ts` 直接使用 `ChatMessage[]` 和 OpenAI Chat 工具消息结构。
- `electron/agent/compress.ts` 按 Chat messages 估算和压缩。

### 2.2 当前上下文层

- 对话、计划、工具结果和验证状态分别保存在不同模块。
- Plan 步骤主要通过工具名称和参数模糊匹配。
- 修改文件后只注入简单的重读提示，没有统一 evidence。
- 测试成功后文件再次变化，不会自动把测试标记为过期。
- 上下文压缩是单一自由文本摘要，无法稳定保存计划状态和验证证据。

### 2.3 当前子代理层

- `dispatch-subagents.ts` 使用全局 runner。
- 多个主会话可能覆盖彼此的子代理执行器。
- 最多 10 个写代理共享同一工作区并行执行，存在文件竞争风险。
- 子代理不完整继承 Skills、MCP、父级取消信号和上下文 revision。
- 子代理结果按完成顺序收集，缺少 stale/conflict 检查。

### 2.4 当前 UI

- 只能看到简单 token 使用量，无法判断上下文是否健康。
- Plan、工具、子代理和文件修改之间没有证据关联。
- 测试结果不会显示是否已过期。
- 模型卡片没有 Responses 能力验证详情。
- 任务“完成”没有可视化验证门禁。

## 3. 目标总体架构

```text
Renderer
  ├─ Chat / Tool Cards
  ├─ Plan Panel
  ├─ Context Panel
  └─ Subagent Panel
          │ IPC events with revision
          ▼
Electron Main Process
  ├─ Context Hub（单一事实源）
  │   ├─ Response Items Log
  │   ├─ Plan State
  │   ├─ Workspace State
  │   ├─ Verification Evidence
  │   ├─ Memory References
  │   └─ Subagent State
  ├─ Agent Loop
  ├─ Session-scoped Subagent Coordinator
  ├─ Responses Client
  └─ SQLite / encrypted API keys
          │
          ▼
POST {providerBaseUrl}/responses
```

核心原则：

1. Context Hub 是任务上下文唯一写入者。
2. Agent 和子代理只读取 Context Selector 生成的最小上下文。
3. 所有状态变化都产生带 sequence/revision 的 Context Event。
4. 文件、测试和子代理结果都必须带工作区 revision。
5. Responses Items 原样保留协议语义，不转换回 Chat messages。
6. UI 通过事件观察状态，不自行推断任务是否完成。

## 4. Responses API 数据模型

### 4.1 领域消息与协议 Items 分离

Renderer 使用的聊天消息改名为领域类型，例如：

```ts
interface SessionMessage {
  id: string;
  role: 'user' | 'assistant';
  content: string;
  attachments?: AttachmentMeta[];
}
```

供应商调用使用独立 Items：

```ts
type ResponseItem =
  | ResponseMessageItem
  | ResponseReasoningItem
  | ResponseFunctionCallItem
  | ResponseFunctionCallOutputItem;

interface ResponseFunctionCallItem {
  type: 'function_call';
  id?: string;
  call_id: string;
  name: string;
  arguments: string;
  status?: string;
}

interface ResponseFunctionCallOutputItem {
  type: 'function_call_output';
  call_id: string;
  output: string;
}
```

禁止在供应商层继续出现 `tool_calls` 和 `tool_call_id`。

### 4.2 工具定义

Responses 工具使用扁平结构：

```ts
interface ResponseFunctionTool {
  type: 'function';
  name: string;
  description: string;
  parameters: Record<string, unknown>;
  strict: boolean;
}
```

跨厂商默认 `strict: false`，后续只有 capability 明确支持时才允许启用 strict。

### 4.3 请求模型

```ts
interface CreateResponseRequest {
  model: string;
  instructions?: string;
  input: string | ResponseItem[];
  tools?: ResponseFunctionTool[];
  tool_choice?: 'none' | 'auto' | 'required' | { type: 'function'; name: string };
  stream: boolean;
  store: false;
  max_output_tokens?: number;
  reasoning?: { effort?: string };
  parallel_tool_calls?: boolean;
}
```

发送前按 provider capability 删除不支持的可选参数，不能因为供应商返回 200 就假设参数已生效。

### 4.4 Endpoint 规则

新增 `buildResponsesUrl(baseUrl)`：

1. 校验非空和 HTTPS（开发环境本地地址按现有安全策略处理）。
2. 移除末尾 `/`。
3. 已以 `/responses` 结尾时原样返回。
4. 否则只追加 `/responses`。
5. 不自动补 `/v1`。
6. 不按域名硬编码供应商分支。

示例：

| Base URL | 最终 URL |
|---|---|
| `https://api.deepseek.com` | `https://api.deepseek.com/responses` |
| `https://dashscope.aliyuncs.com/compatible-mode/v1` | `https://dashscope.aliyuncs.com/compatible-mode/v1/responses` |
| `https://example.com/v1/responses` | 原样使用 |

### 4.5 流式事件

客户端必须支持：

- `response.created`
- `response.in_progress`
- `response.output_item.added`
- `response.output_item.done`
- `response.content_part.added`
- `response.content_part.done`
- `response.output_text.delta`
- `response.output_text.done`
- `response.reasoning_text.delta`
- `response.reasoning_text.done`
- `response.function_call_arguments.delta`
- `response.function_call_arguments.done`
- `response.completed`
- `response.incomplete`
- `response.failed`

规则：

- Function 参数按 `item_id/call_id/output_index` 聚合。
- `response.completed` 读取最终 response 和 usage。
- `response.incomplete` 映射为输出截断并附带 incomplete reason。
- `response.failed` 映射为标准 ErrorMeta。
- 忽略未知事件但保留日志，保证前向兼容。
- 不再等待 `[DONE]`。

## 5. Context Hub 与上下文联动

### 5.1 TaskContext

```ts
interface TaskContext {
  sessionId: string;
  revision: number;
  workspaceRevision: number;
  checkpointId?: string;

  objective: string;
  constraints: string[];
  decisions: ContextDecision[];
  plan: PlanState;
  responseItems: ResponseItem[];

  workspace: WorkspaceContext;
  tools: ToolContext;
  verification: VerificationContext;
  memory: MemoryContext;
  subagents: SubagentContextState[];
  usage: ContextUsage;
}
```

### 5.2 Context Events

```ts
type ContextEvent =
  | UserMessageAdded
  | PlanCreated
  | PlanStepChanged
  | ToolCallStarted
  | ToolCallCompleted
  | ApprovalRequested
  | ApprovalResolved
  | FileRead
  | FileModified
  | CommandCompleted
  | VerificationCompleted
  | SubagentStarted
  | SubagentCompleted
  | MemoryInjected
  | ContextCompacted
  | CheckpointCreated;
```

每个事件必须包含：

```ts
interface ContextEventEnvelope {
  id: string;
  sessionId: string;
  sequence: number;
  contextRevision: number;
  workspaceRevision: number;
  sourceAgentId: string;
  createdAt: string;
  event: ContextEvent;
}
```

主进程按 sequence 串行落库并广播，Renderer 和子代理不能直接改写 TaskContext。

### 5.3 文件联动

`FileModified` 后自动执行：

1. 增加 `workspaceRevision`。
2. 记录文件、修改来源、tool call 和关联 Plan step。
3. 使该文件的读取缓存失效。
4. 将文件标记为 `unverified`。
5. 将关联 Plan step 保持或回退到 `in_progress`。
6. 将基于旧 revision 的测试标记为 `stale`。
7. 将仍在读取旧版本文件的子代理标记为 `context_stale`。

### 5.4 测试与验证联动

每个 Verification Evidence 记录：

```ts
interface VerificationEvidence {
  id: string;
  kind: 'file_reread' | 'typecheck' | 'test' | 'build' | 'manual';
  command?: string;
  relatedFiles: string[];
  planStepIds: string[];
  workspaceRevision: number;
  ok: boolean;
  summary: string;
  createdAt: string;
}
```

文件在 evidence 产生后再次修改时，evidence 自动变为 stale。任务完成门禁只接受当前 workspace revision 有效的 evidence。

### 5.5 Plan 联动

Plan step 扩展：

```ts
interface PlanStep {
  id: string;
  description: string;
  status: 'pending' | 'in_progress' | 'blocked' | 'completed';
  ownerAgentId?: string;
  relatedFiles: string[];
  requiredVerification: string[];
  evidenceIds: string[];
  blockedReason?: string;
}
```

禁止仅根据工具名称自动把步骤设为 completed。完成条件必须来自文件结果和有效 evidence。

### 5.6 Memory 联动

Memory 按作用域选择性注入：

- Planner：需求、架构、约束和历史决策。
- Builder：项目命令、编码约定和已知问题。
- Verifier：验收标准和历史失败。
- Subagent：只注入与分配任务直接相关的记忆。

每条注入记忆记录 source、scope 和 memory id。项目事实与当前文件指纹不一致时标记 `possibly_stale`。

## 6. Token 预算与压缩

### 6.1 预算公式

```text
usableInputBudget
= contextWindow
- maxOutputTokens
- toolReserveTokens
- safetyReserveTokens
```

默认阈值：

- 软阈值：`usableInputBudget * 0.75`
- 硬阈值：`usableInputBudget * 0.90`
- 达到软阈值：异步准备压缩检查点。
- 达到硬阈值：完成压缩前禁止继续调用模型。

不得继续使用简单的 `contextWindow * 0.9` 单阈值。

### 6.2 压缩顺序

1. 去除重复工具结果。
2. 大型文件输出改为路径、范围、摘要和内容哈希。
3. 大型命令输出保留退出码、错误段、开头和结尾。
4. 合并已完成的旧读取和搜索记录。
5. 将已完成阶段转换为结构化 ContextCheckpoint。
6. 保留最近活动轮次。
7. 保留全部未完成工具事务、计划步骤和有效 evidence。
8. 重新估算 token，仍超限时再减少最近保留轮数。

### 6.3 结构化检查点

```ts
interface ContextCheckpoint {
  id: string;
  sessionId: string;
  contextRevision: number;
  workspaceRevision: number;
  objective: string;
  constraints: string[];
  decisions: string[];
  filesChanged: string[];
  verification: string[];
  failures: string[];
  planState: PlanStep[];
  pendingWork: string[];
  createdAt: string;
}
```

创建时机：

- Plan 批准后。
- 一个开发阶段完成后。
- 达到软压缩阈值。
- 一批子代理完成后。
- 应用关闭或任务中断前。
- 变更会话模型前（若未来允许）。

压缩失败时不覆盖上一个有效检查点，也不删除原始 Items。

### 6.4 Reasoning Items

- 当前工具循环内原样保留和回传。
- 不解析、改写或依赖内部文本结构。
- 默认不在 UI 展示原始 reasoning。
- 仅展示状态和 reasoning token 数。
- 供应商返回 encrypted reasoning 时原样本地保存。
- 旧 reasoning 在形成有效检查点后可从活动输入窗口移除，但原始记录仍可按数据保留策略落库。

## 7. Agent Loop 升级

目标循环：

```text
assemble context
  → POST /responses
  → collect output items
  → execute function calls
  → append function_call_output
  → update Context Hub
  → verify / compact if needed
  → next response or completion gate
```

### 7.1 主要变化

- `runAgentLoop` 从 `ChatMessage[]` 改为 `ResponseItem[]`。
- `instructions` 每轮从 Context Selector 重新生成。
- 模型输出的全部 Items 先写入 Context Hub，再执行工具。
- 工具调用使用 `call_id` 关联输出。
- 支持单轮多个 Function Call。
- 只读工具可并行；写工具仍受审批和冲突策略约束。
- Provider capability 控制 reasoning、parallel tools 和 max output。
- 错误重复发生时基于 error fingerprint 终止盲目重试。

### 7.2 完成门禁

调用 `task_complete` 前必须满足：

- 所有必要 Plan steps 已完成。
- 没有运行中的工具和子代理。
- 没有 unresolved approval。
- 所有修改文件拥有当前 revision 的验证 evidence。
- 最近测试没有失败或 stale。
- 没有未解决上下文冲突。
- Agent 已生成面向用户的结果摘要。

不满足时，`task_complete` 返回结构化拒绝原因而不是直接结束。

### 7.3 摘要与记忆

- `summarize()` 改用 Responses API 非流式请求。
- 输入使用 Response Items 或格式化后的结构化数据。
- 记忆提取同样改用 Responses Client。
- 摘要、记忆提取失败不能影响主任务完成，但必须记录可诊断事件。

## 8. 子代理升级

### 8.1 会话级协调器

删除全局 `setSubagentRunner()` 模式，新增：

```ts
interface SubagentCoordinator {
  dispatch(request: SubagentBatchRequest): Promise<SubagentBatchResult>;
  cancel(agentId?: string): void;
  getState(): SubagentContextState[];
}
```

协调器实例绑定 session/stream，不能跨会话覆盖。

### 8.2 子代理定义

```ts
interface SubagentDef {
  id: string;
  task: string;
  role?: 'research' | 'build' | 'verify';
  modelId?: string;
  readOnly?: boolean;
  fileScopes?: string[];
  expectedOutput?: string;
}
```

- `modelId` 只能引用已配置且通过 Responses 验证的模型。
- 缺省继承主模型。
- Research/Verify 可并行。
- Build 默认串行。
- 并行 Build 必须声明不重叠 fileScopes。
- 嵌套深度限制为 1。
- 默认最大并发 4，可在应用设置中降低，不在 v0.9.2 开放无限提高。

### 8.3 子代理上下文包

子代理只接收最小上下文：

```ts
interface SubagentContextPacket {
  parentContextRevision: number;
  workspaceRevision: number;
  task: string;
  role: 'research' | 'build' | 'verify';
  constraints: string[];
  relevantFiles: FileReference[];
  relevantDecisions: ContextDecision[];
  planStep?: PlanStep;
  expectedOutput: string;
}
```

不复制主会话完整历史。

### 8.4 结果合并

子代理返回结构化结果：

```ts
interface SubagentContextResult {
  basedOnRevision: number;
  conclusions: string[];
  filesRead: FileFingerprint[];
  filesChanged: string[];
  verification: VerificationEvidence[];
  decisionsProposed: ContextDecision[];
  unresolved: string[];
  usage: ContextUsage;
}
```

合并规则：

- 只读结论在文件指纹仍一致时直接合并。
- 写入结果必须检查 workspace revision。
- revision 不一致时标记 conflict，不自动覆盖。
- 失败结果保留原因，不抹掉其他成功结果。
- 主 Agent只接收结构化摘要，不接收子代理完整推理日志。
- 父任务取消时级联取消所有子代理和未完成审批。

## 9. 配置、数据库与迁移

### 9.1 配置 schema v2

模型配置增加固定字段：

```ts
interface ModelEntry {
  id: string;
  label: string;
  baseUrl: string;
  model: string;
  wireApi: 'responses';
  contextWindow?: number;
  maxOutputTokens?: number;
  reasoningEffort?: string;
  createdAt: string;
}
```

`wireApi` 只用于明确配置状态，不在 UI 提供选择器。

### 9.2 v1 → v2 迁移

1. 读取并备份 `config.json`。
2. 保留原始模型条目和密钥。
3. DeepSeek 已知模型标记为待 Responses 复验。
4. 自定义模型标记为待复验。
5. GLM/Kimi/MiniMax 标记为 `incompatible_unverified`。
6. 新配置使用临时文件 + rename 原子写入。
7. 迁移异常时恢复 v1 备份，不能回到空配置。

旧会话仍可阅读；绑定不兼容模型时禁止执行，并引导选择通过 Responses 验证的模型。

### 9.3 数据库

新增或扩展存储：

- `response_items`
- `context_events`
- `context_checkpoints`
- `verification_evidence`
- `subagent_runs`

建议字段统一包含 session id、sequence、context revision、workspace revision 和 timestamp。

数据库迁移必须：

- 幂等。
- 可在已有大量会话时执行。
- 不重写旧消息正文。
- 失败时保持旧库可打开。
- 测试升级前、升级后和重复升级。

### 9.4 会话执行上下文

修复 `resolveSessionModel()` 未完整返回 `contextWindow` 的问题，并新增：

- `maxOutputTokens`
- `reasoningEffort`
- `wireApi`
- provider capability

会话继续锁定自己的模型，修改全局 active model 不得重路由旧会话。

## 11. 安全与隐私约束

- Renderer 永远不能获取 API Key。
- `store: false` 固定写入请求，不交给用户关闭。
- Context Event 不记录密钥和完整 Authorization header。
- 日志中的请求体必须脱敏附件路径、密钥和潜在敏感 header。
- 工具输出作为数据 Item 注入，不能拼入高优先级 instructions。
- MCP 输出和网页内容明确标记为 untrusted content，降低 prompt injection 风险。
- 审批绑定 session、agent、tool call、context revision 和 workspace revision。
- 审批后 revision 变化时，旧审批自动失效。
- 外部请求继续遵守 URL guard 和 HTTPS 策略。
