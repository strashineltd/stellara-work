# Stellara Work 安全审查（2026-09-12）

审查基准：工作区 HEAD `639b2bb`，`package.json` 版本 `0.9.3`。本次检查 Electron 主进程及 preload、文件和命令工具、两种 Agent 循环、子代理执行、内置浏览器、模型配置、云账号、MCP、SQLite 存储、安装及发布配置。

发现 11 项代码层面安全问题。10 类异常行为用临时目录中的合成数据或模拟网络/SDK 复现；浏览器权限问题根据代码和 Electron 官方默认行为确认，尚未实际调用摄像头或麦克风。锁文件审计另外报告 10 个受影响依赖包，其中 5 个高危、4 个中危、1 个低危；这是依赖包统计，包含间接传播和开发依赖，不代表 10 个已被利用的客户端漏洞。

本次没有修改应用实现。以下 P1 表示应优先修复，P2 表示随后修复；没有对生产云服务、内网服务或真实用户文件进行攻击。浏览器真实网络竞态、Windows junction 和系统设备权限仍需在对应运行环境复测。

### S01：子代理危险操作跳过审批

`runOneSubagent` 为 Anthropic 和 Responses 两种循环构造选项时均没有传入 `onApproval`。两种循环只在“危险工具且存在审批回调”时等待批准，没有回调就继续调用工具（`responses-loop.ts:445`、`anthropic-loop.ts:271`）。父流程对 `dispatch_subagents` 的一次批准之后，build 子代理可以直接写文件和运行命令，违背每次危险操作均审批的应用约定。

复现：按生产子代理选项创建循环，让模拟模型返回 `write_file`。两种协议均成功写入 `outside-declared-scope.txt`，没有任何审批回调。即使角色提示只允许 `permitted.txt`，仍能写入其他文件，说明 fileScopes 没有执行时约束。此复现不需要访问模型服务。

修复：将父会话审批通道传给所有子代理；危险工具在没有审批回调时默认拒绝。执行入口强制检查只读状态、当前允许工具和规范化后的 fileScopes，而非依赖模型遵守提示。补充拒绝审批、无回调、越过 fileScopes 的负向测试。

### S02：搜索工具越过符号链接

`fast-glob` 默认跟随符号链接，代码仅检查返回路径的字符串是否处于搜索根目录下。后续 `fs.stat` 和 `fs.readFile` 跟随 symlink，缺少 `verifyExistingPath` 的真实路径校验。`search_content`、`search_symbol` 都在只读/计划工具集内，不走危险工具审批。

复现：`project/linked` 指向相邻的 `project-private`。同一个 `linked/secret.ts` 被 `read_file` 正确拒绝，但内容搜索和符号搜索返回了 `SYNTHETIC_OUTSIDE_SECRET`。条件是工作区内存在指向外部的链接；不是无需前提的任意路径读取。返回的内容可能进入模型请求。

修复：关闭 glob 跟随链接，并在读取每个候选文件前对原始工作区根执行真实路径校验。关闭跟随链接不能替代读取入口校验。测试外部文件链接、目录链接、内部链接以及 Windows junction。

### S03：IPv4 映射 IPv6 绕过 SSRF 防护

校验先经过 `new URL`，再检查 `::ffff:` 后缀是否属于点分十进制 IPv4。但是 URL 会将 `http://[::ffff:127.0.0.1]/` 的主机规范化为 `[::ffff:7f00:1]`，使后缀不再满足 `isIPv4`，最终返回允许。映射的 `10.0.0.1` 和 `169.254.169.254` 也被允许。共享此校验的网页抓取和浏览器初始导航均受影响。

复现：普通 `127.0.0.1` 被拒绝，上述三种映射地址均通过；模拟 `fetch` 确认 `webFetch` 进入了网络请求路径。实际连接映射地址取决于操作系统及网络环境，本次没有访问真实本地服务。`web_fetch` 本身仍有主流程审批，绕过的是地址限制。

修复：使用经过验证的 IP 解析器解码所有 IPv4 映射格式，再以地址字节检查网段；补足保留地址范围。DNS 验证应与实际连接使用同一组地址，防止验证后重新解析导致 DNS rebinding。

### S04：浏览器重定向和子资源缺少可靠拦截

`will-navigate`、`will-redirect` 中，仅快速主机名检查失败会同步 `preventDefault()`。对 `127.0.0.1` 等字面量私网地址，快速检查放行，再以 Promise 调用 `validateUrl`，之后才 `stop()`；这个处理不能保证请求发出前阻止。`did-redirect-navigation` 的检查发生得更晚。没有发现浏览器分区上的 `webRequest.onBeforeRequest` 等请求级策略，因此子 frame、图片、脚本及页面发起的请求也未统一经过应用的公共地址规则。

复现：模拟 `will-redirect` 到 `http://127.0.0.1/`，回调返回时既没有 preventDefault，也没有 stop；后续微任务才调用 stop。已确认代码的放行顺序；真实 Electron 中请求是否实际到达目标和子资源的系统网络限制尚未实测。CORS 限制读取响应，不能替代请求目的地址限制。

修复：在会话请求层暂停请求，校验完成后通过回调决定取消或放行，覆盖导航、重定向及所有资源类型。将 DNS 验证与实际连接绑定。相关事件语义见 [Electron webContents 文档](https://www.electronjs.org/docs/latest/api/web-contents#event-will-redirect)。

### S05：附件复制通过 symlink 写到外部

`addAttachments` 创建目标目录并复制文件前，仅对 `target` 和词法形式的附件根做字符串检查，没有验证目标父目录的 realpath 是否仍位于 workDir。项目中的 `.stellara-attachments` 或会话子目录可以是指向外部的链接。

复现：将 `project/.stellara-attachments` 链接到 `project-private`，上传合成 `upload.txt` 后，文件实际创建在外部 `project-private/audit-session/upload.txt`。用户需要执行附件添加动作，目标受会话目录和文件名影响；这里证实的是边界外写入，未声称任意覆盖已有文件。

修复：以已授权 workDir 为原始根校验附件根和目标路径，而不能将可能已被链接替换的附件目录本身当作安全根。拒绝外部目录链接，对目标采用独占创建并处理校验与复制之间的竞态。

### S06：命令路径比较缺少目录分隔边界

`validatePathArg`、`validatePathFlags`、`validateFileArgs` 通过 `resolved.startsWith(path.normalize(cwd))` 判断边界。`/tmp/project-private` 也以 `/tmp/project` 开头，因此 `../project-private/secret.ts` 被允许。路径检查同时忽略 `args.cwd` 改变后的实际参数解析基准，并且未对所有文件参数验证 symlink。

复现：`runCommand({command:'cat ../project-private/secret.ts'}, project)` 成功返回外部合成文件内容。主流程仍会审批 run_command，所以这不是独立的审批绕过；与 S01 的子代理调用结合时后果更大。Node/Python、包管理和构建命令本身能执行任意代码，命令名白名单也不能当作操作系统沙箱。

修复：使用统一 `isWithinDir` 和真实路径规则，参数相对于最终执行 cwd 解析；校验所有形式的路径 flag。若产品承诺命令不能访问工作区外，需要操作系统级文件和网络约束。

### S07：只读 Git 工具执行外部转换程序

`git_diff` 直接运行 `git diff`，没有 `--no-textconv` 或 `--no-ext-diff`，且被工具集归类为只读，不在危险工具审批名单里。Git 文档说明 textconv 在 git diff 中默认启用，会运行配置的外部转换程序。[Git 官方 diff 文档](https://git-scm.com/docs/git-diff#Documentation/git-diff.txt---no-textconv)

复现：在临时仓库的本地 Git 配置中设置 `diff.audit.textconv`，以 `.gitattributes` 为文件选用此转换器。调用 `gitDiff` 后，转换器成功写出合成执行标记。必要前提是攻击者可控制被打开仓库的本地 Git 配置，或能利用已配置的转换驱动；普通克隆仅带 `.gitattributes` 不等于自动注入 textconv 命令。

修复：只读 diff 显式关闭 textconv 和 external diff；同时审查 Git 配置中其他可执行钩子（例如 fsmonitor）及继承环境。针对不可信仓库建立明确的信任流程或隔离策略。

### S08：MCP 禁用和工具白名单未在执行时检查

`getEnabledTools` 会过滤 disabled 服务器和白名单外工具，但 `callTool` 只检查服务器是否存在，随后连接并调用任意工具名。`requiresApproval` 同样不检查 enabled 或 tools。模型返回一个未展示但合法拼接的 MCP 工具名时，执行入口仍会尝试调用；循环也未校验工具名必须属于本轮提供的工具集合。

复现：配置 `enabled:false`、`tools:['permitted']`、`approval:'never'` 的服务器。展示工具列表为空，但 `callTool('mcp__audit__excluded', {})` 仍调用模拟 client，审批策略返回 false。测试注入了缓存连接以避免启动真实 MCP 程序；源代码无缓存时的路径同样没有状态检查。默认 always 策略仍会要求审批，不能把 never 的测试前提省略。

修复：执行前验证 enabled、白名单、服务端实际工具列表及当前运行模式，并在两种循环中检查每个工具名是否属于本轮授权集合。工具配置变更后重新验证，禁用应阻止新调用。

### S09：本地身份和云凭证主体错配

`auth:local:switch` 仅执行 `localAuth.switch`，没有调用已存在的 `cloudAuth.dropSession`。云 access/refresh token 使用全局键名，`buildState` 用全局 refresh token 的存在表示 signedIn，再用当前本地身份的 cloud_link 显示账号。

复现：保留 A 的合成 token，将当前身份从 A 切为 B，`getState` 返回 B 的账号且 signedIn=true，token 仍属于 A，云客户端没有重置。测试模拟存储和 SDK；当前代码未实现云端工作区同步，所以本次未证实云数据跨账号读取，但认证主体错配已存在。异步登录完成时才读取当前 localUserId，也有身份切换期间绑定到错误主体的风险。

修复：切换前先验证目标身份合法，再清理云客户端及会话；或按 localUserId 隔离凭证并核对 token 的账号主体。发起登录、注册时固定操作所属本地身份，异步完成后检查身份未改变。

### S10：远程网页权限请求缺少默认拒绝

内置浏览器分区只设置了下载拦截，没有配置 `setPermissionRequestHandler` 或 `setPermissionCheckHandler`。Electron 官方说明，未自定义处理器时权限请求默认自动批准。因此已批准访问的恶意网页可能请求设备、定位、通知等能力，且应用没有对应的逐项审批流程。[Electron 官方安全文档](https://www.electronjs.org/docs/latest/tutorial/security#5-handle-session-permission-requests-from-remote-content)

本项是静态和文档确认，未实际访问设备。摄像头、麦克风等还受操作系统授权、页面安全上下文和 API 条件限制；应用层缺少审批不意味着能绕过操作系统授权。

修复：在每个浏览器分区创建时同时配置请求和检查处理器，默认拒绝；只对必要能力提供明确的来源核对和用户批准。

### S11：本地身份没有隔离项目、会话和记忆

`local_users` 只用于保存当前身份和云账号绑定。`projects`、`sessions`、`messages`、`memories` 表没有 `local_user_id`，相关 `list/get/search/save/delete` IPC 也不读取当前本地身份。切换本地用户后，用户仍可看到和操作之前身份的工作区、会话、消息和持久记忆；本地用户因此不是安全边界。

这是 schema 和调用路径确认的跨身份数据暴露，不需要恶意模型或网络条件。若“本地用户”只是 UI 标签而非账户隔离，该设计应在界面和文档中明确；若目标是多身份隐私，则当前实现为 P1。

修复：为项目、会话、记忆及附件索引增加 `local_user_id`，所有查询和写入强制使用主进程当前身份；迁移旧数据时明确归属策略。云账号切换也必须与同一身份边界联动。

## 其他加固事项和检查限制

- 工作区授权可被 renderer 自行扩展：无 entryFile 的 `projects:create` 不校验目录是否来自原生选择；`models:updateWorkDir` 和 `settings:update(workDirDefault)` 也能把任意目录加入后续 allowed 列表。若 renderer 已被攻破，可借此扩大文件访问范围。尚未发现独立的 renderer XSS 入口，此项作为条件性加固建议；原生文件选择应产生主进程持有的授权，而非以 renderer 可写配置作为授权依据。
- `configureModel` 在保留旧 key 时允许改 baseUrl。被攻破的 renderer 可把请求目的地改为外部端点，以主进程读取的旧 key 发起请求。应将密钥与来源绑定，变更来源时要求重新授权，远程端点使用 HTTPS；本次未向外部发送任何 key。
- `_cipher` 缺失会降级明文，启动前 dotenv 会将 `.env` 内容放入 `process.env`，命令工具继承这些变量。旧版明文密钥在迁移后仍可能残留环境中；`resetEnvCache` 仅清除 `STELLARA_KEY_`，没有清除其他凭证命名空间。应避免加载凭证条目到全局环境，子进程采用最小环境，并对加密不可用采取明确策略。
- macOS 构建 `hardenedRuntime:false`，发布为临时签名，未看到公证和 Electron fuse 设置。这是发布加固缺口，本次未证明可独立远程利用。
- 输入正则在主进程直接执行，存在灾难性回溯造成卡顿的条件；`webFetch` 响应头收到后即清除超时，读取响应体未保留截止时间。这些可用性风险未执行阻塞复现。
- SQLite 用户数据主要通过绑定参数进入查询；Markdown 使用 ReactMarkdown，未发现启用原始 HTML 执行的路径。渲染隔离、sandbox、webSecurity 和 CSP 均有配置。现有安全相关测试 13 个文件、210 个测试通过，但未覆盖上述边界。
- 本次是源码审查和有界复现，未包含发布二进制逆向、系统沙箱穿透、真实网页网络竞态、云端鉴权规则或生产环境渗透。

## 复现证据与运行方式

在项目根目录执行：

```sh
node --import tsx docs/security-audit/evidence/reproduce-files.ts
```
